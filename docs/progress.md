- [x] B5. ## Phase C: Tools (MCP)
- [x] B7. MCP servers — `avl-mcp` (8101): `get_vehicle_positions` (latest fix per bus with `age_seconds` / `is_stale` computed server-side at request time, world clock, direction; never-reported buses in `missing`), `get_headways` (shared B6 headway logic: status ok/closing/bunched/stale and data quality per pair; terminal buses listed separately), resource `route://{id}/shape` (same GeoJSON as the API). `demand-mcp` (8102): `get_boarding_estimates` (waiting now + arrival rate from recent counts on the world clock, per stop and direction, with data quality), `send_driver_instruction` with its own guards: idempotent `instruction_id` (replay returns the original, a reused key for something else is refused), approval must be approved/edited and match exactly the bus, action and parameters, one instruction per approval (unique constraint, safe under concurrency), GPS fix present and not stale at send time, action valid for the bus's position (upcoming intermediate stops; short-turn only where the bus can turn); stored and published on `vazhisync:instructions`. Tool annotations, Pydantic input/output schemas (`mcp_servers/schemas.py`), structured JSON errors with a `code`, health endpoints, local-only origins for browser tools. Migration 0006: world clock + direction on observations, unique approval per instruction. Acceptance: `tests/integration/test_mcp_servers.py` (in-memory MCP client over real runner data); verified over HTTP against the running stack.
- [x] B8. MCP client and agentic harness (part 1) — `app/harness/`: every agent tool call goes gate (per-agent allowlists; only `dispatch` may send, rule 5) → budget (whole-run time limit, tool calls per agent, graph steps for B10) → pre-hooks → call (per-call timeout capped by the run's remaining time, retries with backoff for connection errors/timeouts only, per-server availability circuit: a failed server is logged `tool_unavailable` once and fails fast for a cooldown, then one probe; `tool_available_again` on recovery) → result validation against the B7 Pydantic models (structured server errors keep their `code`) → post-hooks. The send pre-hook duplicates the server guards on purpose: approval approved and matching, unused, and GPS fresh via avl-mcp (fails closed if avl-mcp is down). `call_optional` turns an unavailable non-critical tool into an explicit degraded result. Every line carries the run_id. Discovery logged at API startup in the background. MCP client = the official SDK (`langchain-mcp-adapters` 0.3.1 breaks on MCP SDK v2; decisions.md #8). Acceptance: `tests/integration/test_harness_mcp.py` (real servers over HTTP, demand-mcp killed) and verified against the Docker stack: stopping `demand-mcp` → `tool_unavailable`, degraded, avl unaffected, recovered after restart.

## Phase D: The brain

- [x] Added (with the user, before B14): AG-UI run stream for the officer console (decision 10) — own SSE endpoint emitting `ag_ui.core` events fed by LangGraph's `astream` in the worker (the official adapter can't attach to runs it didn't start). `GET /officer/runs`, `GET /officer/runs/{id}/events` (attach any time: snapshot + live tail from a Redis Stream, `Last-Event-ID` reconnect, DB fallback), `POST /officer/runs/{id}/agui` (RunAgentInput.resume → the same decision service as the REST endpoint, then the resumed segment's stream). Tests: `tests/unit/test_agui_view.py`, `tests/integration/test_agui_stream.py`.
- [x] B9. LLM gateway and agentic harness (part 2) — own thin gateway (`app/llm/gateway.py`, decision 9), no new dependency: Groq gpt-oss-120b → Groq qwen3.8-27b → OpenRouter gemma-4-31b-it:free → local qwen3:8b → rules; tiers without a model/key are skipped. Per-call timeout; retries only for timeouts / connection / 5xx; 429 → next tier + cool-down; malformed or check-failing JSON → one repair with the exact problems, then the next tier; inside a run every call is capped at the run's remaining time minus `LLM_TIME_RESERVE_SECONDS`. Token budgets per run and per agent (estimated before the call; over budget → rules, never the call). Every attempt and every rules answer is an `llm_usage` row (tier, model, tokens, cost, latency, error kind) and, with real keys, a Langfuse generation (best effort). Context builder `app/harness/context.py`: compact pair/bus summary, the stops the rules allow, existing and officer-rejected options, past measured outcomes. Agents: the Action Generator adds up to 3 LLM ideas (checked against the allowed stops, made canonical, then rulebook-checked and simulated like rule candidates; stored with source `llm`); the Control Advisor's explanation is LLM-worded from the simulator's numbers, and any number the context didn't give rejects it (template kept). The ranking never changes (rule 2). Acceptance: `tests/unit/test_llm_gateway.py` (primary 503 → backup answers, both attempts logged; exhausted budget → rules without calling a model) and `tests/integration/test_llm_workflow.py` (the same in a real run, rows carry the run id). Live in Docker without keys: qwen3:8b took > 74 s, was cut off at the run limit, rules answered and the runs paused for the officer normally. With the keys: Groq gpt-oss-120b answers both agents in ~1 s (reasoning_effort low), LLM ideas are simulated and LLM-worded explanations reach the officer; the free OpenRouter Gemma tier was rate-limited upstream when checked (the gateway skips it).
- [x] B10. Agent workflow with LangGraph (rules only) — one graph (`app/graph/workflow.py`): Headway Monitor (freshness + still bunched, via avl-mcp) → Action Generator (hold the follower for the deficit and half of it, leader skips its quietest stops when demand data is up, short-turn when the other direction has a ≥1.5× gap; rulebook R1–R6 and past outcomes filter) → Impact Simulator (`from_observations` from tool results only, `Send` fan-out one branch per candidate, 3 seeds with common random numbers, per-sim timeout + semaphore) → Control Advisor (simulator benefit vs do nothing, R7 rejects added bunching, do-nothing can win, near-ties escalate). Conditional ends: stale → flagged (event reopened for retry), not bunched → resolved. One active run per bus pair (row-locked claim), repeated events deduplicated; runner queues `run_workflow` on the ARQ worker when it opens an event, a minute sweep retries open events with no active run. Step budget, run time limit, typed failures (tools down / budget / timeout → run failed, event reopened). Every node → `agent_steps`; `candidate_actions` and `recommendations` stored. AgentSpecs in code and `docs/agents.md`; hard rules in `docs/rulebook.md`. Acceptance: `tests/integration/test_workflow.py` (runner-detected event → ranked recommendation through the real MCP servers; e.g. hold 180 s vs skip 2 stops within the near-tie margin → escalated).
- [x] B11. Counterfactual simulation workers — each `Send` branch submits exactly one ARQ job to a dedicated `sim-worker` (own queue `vazhisync:sims`, so workflow runs waiting on simulations can't deadlock the worker) and awaits it with a hard wall-clock timeout; timed-out jobs are aborted. The payload is the MCP observations + candidate only (rule 1). Jobs run in a pre-warmed process pool (the simulator is CPU-bound pure Python; threads would serialise on the GIL), concurrency `SIM_CONCURRENCY`. `simulation_jobs` records pending → running → completed / failed / timed_out. 5 seeds per candidate with common random numbers: paired per-seed benefits vs do nothing → mean with a 95 % confidence range ("saves 144 ± 54"), a bad case (10th percentile) for the safest option, and overlapping ranges count as a near-tie. Acceptance: `tests/integration/test_sim_jobs.py` — four candidates in parallel, whole workflow ~2 s; a hung job times out at the limit while the other three are ranked. Verified in Docker (4 jobs ≈ 0.5 s each on the sim-worker).

## Phase E: Human control
- [x] B12. Approval, dispatch and driver feedback — the graph pauses with LangGraph `interrupt()` and is checkpointed in Postgres (`langgraph-checkpoint-postgres`, own `langgraph` schema; thread id = run id); `workflow_runs.waiting_for` (officer / driver / outcome) and a row-locked claim make every resume exactly-once. Officer: `GET /officer/recommendations`, `POST /officer/recommendations/{id}/decision` — approve → dispatch; edit (hold length) → re-simulate → back to the officer (even if the edit loses); reject with a reason → next round without that option (max 2 rounds); recommendations expire after 90 s (→ re-plan from fresh data); one approval per recommendation (double-click → `already_decided`). Dispatch re-validates with fresh MCP data right before sending (pair recovered → no send), instruction id derived from the approval (`apr-<approval_id>`), passenger notices for skip-stop / short-turn. Driver: current / ack (applied by the world's bus on the next tick) / done / can't-comply (blocking traffic, bus full, other → cancelled, officers alerted, re-plan); no ack in 120 s → expired, re-plan. Outcome measured ~15 world-minutes after the ack from observed queues → `intervention_outcomes` with predicted AND actual benefit (the generator's past-outcome filter uses it). An officer-waiting run whose recommendation expired is superseded by a new event for the pair (otherwise an ignored recommendation would block the pair forever). Migration 0007. Acceptance: `tests/integration/test_approval.py` — API + worker restarted while a run waits → approve still resumes and sends; five concurrent approves → one instruction. Verified in Docker: approval → resume from checkpoint → re-validation found the pair recovered and correctly sent nothing.
  - Follow-up (after the AG-UI stream): runs from before B12 that *ended* with status `awaiting_approval` / `escalated` still blocked their pairs; a run now counts as active only while `finished_at` is null (claims and the retry sweep).
  - Follow-up (with B9): a worker that died mid-run left the run `running`, and runs paused before migration 0007 had no `waiting_for`; both blocked their bus pairs forever (seen live: 181 events skipped). Migration 0008 adds `workflow_runs.last_active_at` and marks the old paused runs as waiting for an officer; a run idle past 2x the run limit is closed as `abandoned`.

## Phase H: Extensions
- [x] B21. Early warning — `app/agents/early_warning.py`: a new `early_warning` agent (read tools only) runs every 30 s (ARQ cron): avl-mcp positions + headways and demand-mcp estimates through the harness → `from_observations` (the Impact Simulator's own observation builder) → "do nothing" stepped 15 min over 3 seeds, pair headways checked with the live detector's `compute_headways`. A pair that is fine now (fresh, ok/closing) but bunches in ≥ 2 of 3 seeds raises a *predicted* bunching event (migration 0009: `kind`, `predicted_in_seconds`) and starts the workflow. Same one-run-per-pair claim, rulebook and cooldowns; no prediction while an event is open for the pair or within 5 min of the last one. The Headway Monitor and dispatch's last check accept a predicted pair that isn't bunched yet (stale GPS still stops it, rule 4); the world runner ignores predictions; the retry sweep dismisses stale ones instead of retrying; a world reset voids them. Acceptance: `tests/unit/test_early_warning.py` — on the golden `normal_morning_peak` the first bunch (32B-04 behind 32B-03) forms at 15.0 min and is predicted at 3.0 min; a 60 s hold then keeps the pair apart for 15 min, while once bunched no hold up to the 180 s limit does. Plumbing: `tests/integration/test_early_warning.py`. Sweep cost ~0.3 s CPU (in a thread). Live at 1×: predictions every few minutes, 1–15 min ahead; most runs end "do nothing" (over 15–30 min the simulator finds a single-pair hold costs more passenger-minutes than it saves because the whole route bunches anyway — the simulator decides, rule 14), some go to the officer. Event lifecycle fixed on the way: the runner closes events left 'handling' by a do-nothing run (and reloads them after a restart), superseded / abandoned runs dismiss their event, a do-nothing prediction is dismissed, migration 0010 dismisses the events already stuck (1,088 on the dev DB).
- [x] B22. Case retrieval — pgvector in the database image (`backend/docker/postgres/Dockerfile`, CI installs it into the service), migration 0011 (`CREATE EXTENSION vector`, `cases`, `recommendations.similar_cases / confidence / confidence_note`). A case = 9 normalised features from MCP observations (gap ratio, route position, direction, time of day sin/cos, observed-speed factor in place of weather, leader/follower load, leader next-stop demand) + action + predicted benefit; recorded when an instruction is sent, completed with the actual benefit when the outcome is measured. Retrieval (`app/harness/cases.py`, L2 nearest neighbours within 0.6, top 3) in the Action Generator: the cases go into the LLM context, a hold that worked in a similar case is offered again (checked and simulated like any candidate), and they're stored on the recommendation for the officer's card (REST and AG-UI view). Confidence is lowered, with a note computed in code, when ≥ 2 similar measured cases of the recommended action delivered < 70 % of their predicted saving. Acceptance: `tests/integration/test_cases.py` — the repeated bunched scenario retrieves its earlier case (distance < 0.05) and `GET /officer/recommendations` shows it with predicted and actual saving. Unit: `tests/unit/test_cases.py`.
